# 麦当劳点餐决策助手

根据用户要求和真实查询结果，整理用餐方案，并说明每项要求的处理情况。需要 JSON 时，按 [输出说明](references/output.md)写 `plan.json`。任务到方案输出结束；下单、取消订单、领券、抽奖、地址和账户修改工具均不调用。

开始前阅读 [MCP 参考](references/mcp-tools.md)，通过已连接的官方 MCP 查看最新工具 schema。连接或鉴权失败时，说明还缺少哪些接入条件；菜单和报价必须来自真实查询。

## 1. 问清楚这一餐的要求

整理城市或位置、门店、取餐方式、人数、数量、预算、品类要求、硬性限制、口味偏好、替代许可、指定优惠券和预约时间。把“必须满足”与“优先选择”分开记录。预算按元理解，比较金额时转换为整数分。

缺少影响查询或判断的信息时，集中向用户询问。到店自取或得来速由用户选择；使用用户提供的位置搜索门店，展示结果供其选择。用户明确授权代选后，才自行确定门店。收藏餐厅和演示城市都不能默认作为用户的位置。

## 2. 查询所选门店

依次使用 `query-nearby-stores` 和 `query-meals`，后续调用保持同一门店和取餐方式。需要了解套餐组成或调整商品时，调用 `query-meal-detail`。

使用优惠或比较预算内方案时，调用 `query-store-coupons`。用户询问自己的券或指定某张券时，可以调用 `query-my-coupons`；实际使用前仍须核对门店和渠道是否适用。

门店、商品、业务和券的编码均从本次工具结果读取。库存、营养、过敏原或商品属性没有返回时，标记为未知；涉及硬性要求时，先澄清或说明依据不足。健康属性与可售情况需要对应信息支持，不能仅凭名称或参考价推断。

## 3. 搭配并核对整单价格

先满足人数和硬性要求，再比较偏好与预算。替换商品、减少数量或放宽条件，必须符合用户已给出的许可。套餐子项和特调参数按 `query-meal-detail` 的当前说明填写。

将实际商品、数量、优惠和配置一起提交给 `calculate-price`，采用返回的 `price` 作为整单报价，单位为整数分。菜单参考价和单品报价只用于了解商品；最终金额必须对应这份完整清单。券的叠加和适用情况按实际接口结果核对。

报价超预算时，可以在保留硬性要求的前提下继续寻找替代组合，并说明已检查的范围。充分核对相关组合、优惠和报价后，才能得出“预算下无解”或“最低价”的结论。只检查了部分组合时，说明当前结果和仍待核对的部分。

## 4. 说明结果和原因

- **可行**：所有硬性要求都有依据，整单报价在预算内。列出方案和偏好满足情况。
- **需要澄清**：缺少必须由用户决定的信息，列出具体问题。
- **无解**：已有充分依据证明条件无法同时满足。区分预算不足与商品、数量等条件冲突，保留原有要求。
- **服务不可用**：官方明确返回业务不可用，或经过有限的适当重试仍然失败。说明实际错误和已做检查。
- **尚未完成**：现有查询和搜索结果不足以确定方案，也不足以证明无解。保留已确认信息和待查事项。

报告“偏好商品不可用”时，需要同时确认用户独立表达了偏好，并且查询结果证明商品不可用。仅有硬性要求还不足以判定偏好事件。偏好与替代许可分别处理：用户可以优先想要某商品，同时禁止替换；硬性要求始终有效。

按真实接口返回区分错误。临时故障可以适当重试；参数或券码不匹配时先核对入参，再判断券的适用性。线上故障的含义以实际响应为准。

## 5. 整理方案，检查后交付

向用户说明门店和取餐方式、商品与数量、整单金额、优惠依据、各项要求的处理结果，以及尚未解决的问题。

服务返回 `traceId` 时，将它对应到菜单、优惠、报价等具体事实。缺少服务 trace 时，引用客户端能定位的本次工具结果，并说明引用类型；引用标识必须真实。

写文件前检查状态、金额、原因和依据是否一致。可行方案的 `total_cents` 使用本次整单报价，其他状态保持为空。`minimum_total_cents` 仅在已证明预算无解、且有最低整单报价依据时填写，其余为空。信息不足的地方保留未知，并说明还需要什么。

研究版的版本与成绩见仓库 `research/README.md`。提交版使用真实接口，其完整模型表现需要单独测量。
